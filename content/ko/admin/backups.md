실제 용도로 사용한다면 마스토돈 서버를 반드시 정기적으로 백업해야 합니다.

## 개요 {#overview}

중요도 순서로 백업해야 할 항목은 다음과 같습니다.

1. PostgreSQL 데이터베이스
2. `.env.production` 파일이나 이에 준하는 위치의 애플리케이션 비밀 정보
3. 사용자가 업로드한 파일
4. Redis 데이터베이스

## 장애 유형 {#failure}

일반적으로 대비할 장애에는 두 가지 유형이 있습니다. 디스크 데이터 손상 같은 하드웨어 고장과 특정 데이터의 잘못된 삭제 같은 사람 또는 소프트웨어의 오류입니다. 이 문서는 첫 번째 유형만 다룹니다.

마스토돈은 가장 중요한 모든 데이터를 PostgreSQL 데이터베이스에 저장합니다. PostgreSQL 데이터베이스를 잃으면 모든 계정과 게시물, 팔로워를 포함해 서버 전체가 작동하지 않게 됩니다.

애플리케이션 비밀 정보를 잃으면 일부 기능이 작동하지 않습니다. 사용자가 로그아웃되고 2단계 인증을 사용할 수 없게 되며 Web Push API 구독도 작동하지 않습니다.

사용자 업로드 파일을 잃으면 아바타, 헤더, 미디어 첨부 파일을 잃지만, 마스토돈은 이후에도 _작동합니다_.

Redis 데이터베이스 손실은 거의 무해합니다. 복구할 수 없는 데이터는 Sidekiq 큐의 내용과 이전에 실패한 작업의 예약된 재시도뿐입니다. 홈과 리스트 피드는 Redis에 저장되지만 tootctl로 다시 생성할 수 있습니다.

가장 좋은 백업은 마스토돈 자체와 같은 컴퓨터에 저장하지 않는 이른바 외부 백업입니다. 호스팅 서버에 불이 나서 하드 디스크가 폭발한다면 같은 하드 디스크에 보관한 백업은 큰 도움이 되지 않습니다.

## 애플리케이션 비밀 정보 백업 {#env}

애플리케이션 비밀 정보는 변하지 않으므로 가장 쉽게 백업할 수 있습니다. `.env.production`을 안전한 곳에 보관하기만 하면 됩니다.

## PostgreSQL 백업 {#postgresql}

PostgreSQL은 정전, 하드 디스크 고장, 잘못된 스키마 마이그레이션으로 데이터가 손상될 수 있습니다. 따라서 가끔 `pg_dump`나 `pg_dumpall`로 백업하는 것을 권장합니다.

고가용성 구성에서는 핫 스트리밍 복제로 항상 최신 데이터를 갖는 두 번째 PostgreSQL 서버를 유지하고, 다른 서버가 중단되면 전환할 수 있도록 준비할 수 있습니다.

## 사용자 업로드 파일 백업 {#media}

Amazon S3, Google Cloud, Wasabi 같은 외부 객체 스토리지 제공자를 사용한다면 해당 파일의 백업은 걱정하지 않아도 됩니다. 각 회사가 하드웨어 고장을 처리할 책임이 있습니다.

로컬 파일 스토리지를 사용한다면 업로드 파일이 기본적으로 저장되는 대용량 `public/system` 디렉터리의 사본을 직접 만들어야 합니다.

## Redis 백업 {#redis}

Redis 백업은 쉽습니다. Redis는 정기적으로 `/var/lib/redis/dump.rdb`에 기록하므로 이 파일 하나만 복사하면 됩니다.
